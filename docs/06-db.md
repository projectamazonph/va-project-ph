# Database Design & Operations

Version: 1.0 · Reviewed: 2026-08-17 · Owner: Backend Lead
Engine: Supabase PostgreSQL · Client: `@supabase/ssr` + `@supabase/supabase-js` · Migrations: `supabase/migrations`

## Principles

Additive migrations only in production. Column/table removals go through: deprecate -> backfill -> remove (3 releases).
Every migration ships with rollback notes.
Never edit an applied migration. Never migrate reset against shared/prod databases.
UUID primary keys everywhere (no enumeration).
createdAt/updatedAt on every table; soft-delete (deletedAt) for user-facing records.
Indexes must justify themselves in the migration comment.

## Entity-Relationship Overview

```
User ---- Lesson ---- User(teacher)        // cohort assignment
User ---- QuizQuestion
User ---- TrainerCase >-- TrainerRow
User ---- CoachMessage
Teacher ---- Student
Teacher -- (admin/audit)
```

[The first Supabase migration is in `supabase/migrations/202608180001_learning_foundation.sql`.
Future schema changes must ship as additive migrations with rollback notes.]

## Seeding Strategy

- Synthetic seeds for dev/staging (deterministic; CI snapshot-tested).
- Anonymized prod snapshot for staging (never real student PII).
- Seed runner: deterministic SQL or a repository-owned seed command; never use
  real student PII in development or CI.

## Backup & Restore

- Nightly encrypted snapshot to object storage (S3-compatible).
- Restore drill quarterly (16-runbooks.md).
- WAL archive kept 7 days; full snapshot kept 30 days.
